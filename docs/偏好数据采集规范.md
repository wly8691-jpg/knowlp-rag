# 偏好数据采集规范（采集端）

> 背景：KnowLP 偏好学习（T2）要从「成对偏好」学图权重，替代手工调权重。
> 2026-08-23 实测：被动收的 consumed/ignored 数据撑不起——99 个偏好对、23 条边全单向
> （纯 chosen 或纯 rejected），BT 模型学不到对比信号，权重发散到边界。
> 所以要改记录方式：从「用了/没用」升级到「哪个比哪个更相关」。

## 一、核心转变

| | 现在（隐式，撑不起） | 要改成（显式，能学） |
|---|---|---|
| 记录什么 | consumed（用了）+ ignored（没用） | chosen ≻ rejected（A 比 B 更相关） |
| 数据形态 | 单向：边永远 chosen 或永远 rejected | 双向对比：同一条边有时 chosen 有时 rejected |
| rejected 选谁 | 所有没用到的边 | 最接近但不相关的边（hard negative） |

BT 模型 `P(A≻B)=σ(w_A−w_B)` 要的是**对比信号**：同一条边在不同 query 下有时赢有时输，
才能学到中间权重。单向数据只会把权重推到上限或下限，学不出东西。

## 二、什么时候记

1. **检索结果不对**：该读 A 却返回了 B → 记一条 `(A ≻ B)`（A 比 B 更相关）
2. **D-Optimal 主动问**：回答「这条边对不对」→ 记一条 `(对的 ≻ 错的)`
3. **纠正**：用户/你发现某条边权重该升、某条该降 → 记成边对，别只记"这个不对"

## 三、记什么（字段）

每个纠正事件 = **一个边对**，带上下文：

```
session_id   会话（轨迹级上下文，别丢）
query        当前查询
timestamp    时间
chosen       更相关的边   {from, to, type}
rejected     不那么相关的边 {from, to, type}
```

接口仍走 `knowlp_record_feedback`，但语义升级：
- `consumed` = chosen（真的更相关的边）
- `ignored` = rejected（选「最接近但不相关」的，不是把没用的全塞进来）

## 四、三条硬规则（决定数据能不能用）

1. **rejected 选 hard negative**：选「看起来相关、实际不相关」的边，别选完全无关的。
   BT 靠对比学精细权重，hard negative 才有信息量。例：查「RAG 架构」，返回了
   「RAG检索架构」和「向量数据库选型」——前者相关、后者只是沾边，后者才是好 rejected。

2. **避免单向**：同一条边，不同 query 下要有「有时 chosen、有时 rejected」的记录。
   永远把某条边标 chosen（或永远标 rejected），等于没给对比信号。

3. **避免笛卡尔积**：一次纠正 **1 个 chosen 对 1–2 个 rejected**，别「1 对 N」全配对——
   那是把 1 个信号放大成 N 个假样本，还制造单向边。

## 五、反例对照

| ❌ 不要这样 | ✅ 要这样 |
|---|---|
| 这次检索：用了 `index`，没用 `data-sources/profile-a-vs-b/...`（22 个全记 ignored） | 这次检索：`index` 比 `data-sources` 更相关，记 `(index ≻ data-sources)` 一条 |
| 每次都把 `index||xxx` 记 chosen | 不同 query 下，`index||xxx` 有时相关有时不相关，如实记 |
| rejected 记「完全无关」的边 | rejected 记「最接近但不相关」的边 |

一句话：**别报「我用了啥没用啥」，报「这个比那个更相关」**——每次一条清晰的方向对比。
